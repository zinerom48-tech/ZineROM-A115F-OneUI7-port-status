## Failed approaches that must not be repeated

1. Generating another ZIP with unrelated changes before the `enablefilecrypto` root cause is identified.
2. Treating `wait_for_keymaster` breadcrumbs as a fix. They are diagnostic only.
3. Treating `K00R` or QSEE `0x72000206` as a confirmed root cause; both occur on booting devices.
4. Adding another Keymaster bridge or changing FBE/fstab without a raw vold/keystore2 log.
5. Disabling FBE or formatting `/data`, `/keydata`, or `/keyrefuge` as a blind workaround; this destroys data and does not prove the underlying Keymaster path works.
6. Assuming the donor system is 64-bit-only without checking; it declares 32-bit ABI support and ships 32-bit binaries. The remaining 32-bit risk is library-level, not architectural.
7. Treating a truncated ext4 listing as proof that a library is absent. The first `/system/lib64` result ended at `read beyond end of image`; the directory data was simply outside the decompressed prefix.
8. Flashing on a different model/bootloader or a device without a verified stock restore path.
9. Claiming “boot fixed” from static tests, CRC checks, or package validation alone.
10. Treating `A115F_KEYMASTER_BARRIER_COMPLETE` as proof that KM4 is ready; the helper only waits for Keystore2 and does not fail on `getSecurityLevel` errors.
11. Moving the barrier into vendor `on post-fs-data`; system `installkey /data` runs before that trigger, so the barrier would be useless.
12. Treating the first `on init` `QSEECom_start_app failed` as the root cause. That start precedes the `/vendor/firmware_mnt` mount and is expected to abort; the late-fs start is the one that matters.
13. Rebuilding from `manus/a115f-build-once` or `manus/a115f-bootability-preflight` and assuming the barrier is included. Neither branch contains `scripts/patch_a115f_init.py`.
14. Claiming “Android 15 removed legacy fscrypt support.” AOSP/LineageOS 22.2 (Android 15) and 23.1 (Android 16) still contain `isFsKeyringSupported`, `installKeyLegacy`, and `evictKeyLegacy`. The removal is Samsung-specific in the donor binaries.
15. Replacing `/system/bin/init` with a wrapper that does not preserve `argv[0]` or verify the `ueventd` symlink. `/system/bin/ueventd` is a symlink to `init`, and `service ueventd … seclabel u:r:ueventd:s0` starts it through that path; the wrapper must pass ueventd through and both init files need `init_exec` for the post-policy `second_stage` re-exec.
16. Trying to inject a session keyring into PID 1 from a helper. `keyctl_session_to_parent()` rejects `parent->pid <= 1`; PID 1 must create the keyrings itself.
17. Assuming a healthy KM4 is sufficient. Even with perfect Keymaster/Keystore2 behavior, the shipped donor `vold` cannot install a key into the A11 4.9 kernel, and donor `init` provides no keyring for `request_key` to search.
18. Treating the current `f51460ef…` asset as safe to re-test for a boot outcome. It cannot succeed at FBE on this kernel regardless of KM4; a diagnostic run can only confirm the failure stage.
19. Working around the missing `linux-modules-extra-<kernel>` package by shadowing `uname`/`sudo`, installing a dummy package with that name, adding a local apt repository from a test step, pinning a specific kernel package, or disabling the step. Ubuntu publishes no matching package; the defect is the workflow’s `linux-modules-extra-$(uname -r)` line, and the missing name changes with the runner pool (`7.0.0-1014-aws`, then `7.0.0-1017-azure`). Fix that line directly and keep the build evidence honest.
